# ADR 0001. Жизненный цикл оригиналов и альбомов с накоплением знаний

- Статус: предложено
- Дата: 2026-11-07
- Связано: [ADR 0002](0002-learned-photo-selection.md) - журнал решений и
  обучаемый отбор

## Контекст

Ailbum собирает демо альбома для заказа на сайте фотокниг или готовит изображения
для печати в типографии. Пользователь работает с одной базой
`.ailbum/ailbum.sqlite3` годами: после заказа альбома оригиналы удаляются с диска,
потому что занимают много места, а база лиц и предпочтения в выборе должны
сохраняться и улучшать следующие альбомы.

Текущее состояние (схема версии 11, раскладка альбома из `src/ailbum/layout/`):

| Проблема | Где | Последствие |
| --- | --- | --- |
| Нет сущности альбома | `photo_selections`, `desktop_run_settings`, `layouts.run_id UNIQUE` привязаны к `analysis_runs` | Альбом = запуск анализа; повторный анализ тех же фото начинается с пустого выбора и без раскладки |
| Удаление оригинала неотличимо от временного отсутствия | `images.missing` | Отключённый внешний диск и сознательное удаление выглядят одинаково |
| Каскадное удаление по `images` | `photo_analysis`, `faces`, `photo_selections`, `layout_placements`, `image_object_scans` - `ON DELETE CASCADE` | Любая "чистка" `images` стирает эмбеддинги лиц, ручные исправления, выбор и раскладку заказанного альбома |
| Центроид человека считается только по строкам `faces` | `_refresh_person_centroid` | Потеря лиц размывает или замораживает базу людей |
| UI скрывает `missing = 1` | `get_desktop_library`, `_initialize_desktop_selection` | Заказанный альбом исчезает из интерфейса вместе с оригиналами |
| Миниатюры и превью читают оригинал | `desktop_bridge._face_thumbnail`, `ailbum-media://`, `layout/assistant.render_variants` | Без оригиналов пусты карточки людей, сетка и превью разворотов |
| Экспорт не фиксируется | `layout/export.export_originals` | Неизвестно, был ли альбом выгружен полностью; `missing` из результата экспорта нигде не сохраняется |
| Пожелания к раскладке не сохраняются | `LayoutParams.prompt` используется в `service.generate`, но не пишется в `layouts` | Текстовые предпочтения ("больше пейзажей") теряются после генерации |
| Идентичность изображения = абсолютный путь | `images.path UNIQUE`, `_upsert_image` | Тот же файл, вернувшийся из бэкапа по другому пути, становится новым изображением без истории |
| Кэш признаков по SHA-256 никогда не чистится | `.ailbum/feature-cache/` | Для удалённых оригиналов кэш - мёртвый вес |

ADR 0002 (принят, не реализован) вводит журнал `selection_events` и таблицу
`ranking_models`. В нём указана схема v11, но v11 уже занята раскладкой; ADR 0002
должен получить следующую свободную версию. Этот ADR использует его журнал как
есть и только требует, чтобы журнал переживал архивацию оригиналов.

## Решение

Разделить данные на три слоя с разным сроком жизни и сделать удаление оригиналов
явной операцией "архивации", которая никогда не трогает накопленные знания.

```text
Слой 1. Оригиналы (на диске, временно)
    файлы фото, feature-cache                  -> удаляются после заказа
Слой 2. Прокси (в .ailbum/, компактно)
    превью ~1600px, кропы лиц                  -> живут, пока жива запись images
Слой 3. Знания (в SQLite, навсегда)
    images (метаданные + sha256), photo_analysis, faces + эмбеддинги, people,
    image_object_scans, albums, album_photos, layouts*, selection_events,
    ranking_models
```

### 1. Альбом - самостоятельная сущность

Новая таблица `albums`:

- `id`, `public_id` (UUID), `title`;
- `purpose`: `photobook_demo` | `print`;
- `status`: `draft` -> `ordered` -> `archived`;
- `target_count`, `run_id` (текущий запуск анализа, `ON DELETE SET NULL`);
- `ordered_at`, `archived_at`, `created_at`, `updated_at`.

`album_sources(album_id, source_root)` - каталоги, из которых собран альбом.

`album_photos(album_id, image_id, position, added_at)` заменяет `photo_selections`.
Ключ - `(album_id, image_id)`, а не `run_id`: повторный анализ с новыми
параметрами меняет рекомендации, но не сбрасывает ручной выбор.
`desktop_run_settings.target_count` переезжает в `albums`.

Раскладка переходит к альбому: `layouts.run_id UNIQUE` заменяется на
`layouts.album_id UNIQUE REFERENCES albums(id) ON DELETE CASCADE`, `run_id`
остаётся обычной колонкой (из какого анализа взяты факты). `selection_hash`
считается по `album_photos`, флаг `stale` работает как раньше. Повторный анализ
не удаляет раскладку, а помечает её устаревшей, если изменился выбор.

В `layouts` добавляется `prompt TEXT`: текст пожеланий сохраняется вместе с
раскладкой и становится частью накопленных предпочтений.

### 2. Журнал решений - по ADR 0002

`selection_events` и `ranking_models` определяет ADR 0002. Требования этого ADR:

- `selection_events` получает колонку `album_id` (`ON DELETE CASCADE`), чтобы
  события ручного выбора относились к альбому, а не только к запуску;
- признаки кадра не копируются в событие: обучение ADR 0002 соединяет события с
  `photo_analysis` и `faces`, и эти строки после архивации остаются (п. 4);
- обучение по архивным альбомам не требует оригиналов, потому что вектор признаков
  ADR 0002 строится из строк БД.

Если этот ADR реализуется раньше ADR 0002, `selection_events` создаётся здесь в
форме ADR 0002 плюс `album_id`.

### 3. Состояние доступности оригинала

`images.missing` заменяется на `images.availability`:

| Значение | Смысл | Как попадает |
| --- | --- | --- |
| `present` | файл на месте | индексация нашла файл |
| `missing` | файла нет, причина неизвестна | индексация не нашла файл (диск отключён, переименование) |
| `archived` | оригинал сознательно удалён | операция архивации альбома или ручное подтверждение |

Правила:

- индексация переводит `present -> missing`, но никогда не трогает `archived`;
- `missing` и `archived` изображения не участвуют в новом CV-анализе и в
  `export_originals`;
- UI показывает `archived` фото через прокси, `missing` - с пометкой "нет файла"
  и действием "подтвердить удаление" (-> `archived`).

### 4. Удаление строк запрещено каскадом

Внешние ключи на `images(id)` из `photo_analysis`, `faces`, `album_photos`,
`layout_placements`, `selection_events` меняются на `ON DELETE RESTRICT`.
`image_object_scans` остаётся с `CASCADE`: это кэш, но при архивации его строки не
удаляются, потому что нужны для пересборки раскладки без оригиналов. Архивация -
это `UPDATE`, а не `DELETE`. Удалить строку `images` можно только командой
"забыть" (п. 8).

`faces` и их эмбеддинги остаются навсегда: SFace-эмбеддинг - 128 float32 = 512 байт,
10 000 лиц - около 5 МБ. Поэтому `_refresh_person_centroid` продолжает работать по
всем лицам человека, включая лица из архивных альбомов, а ручные переносы лиц и
объединения людей не теряются.

### 5. Прокси создаются до удаления оригиналов

Каталог `.ailbum/proxies/`:

- `photos/<sha256>.jpg` - длинная сторона 1600 px, JPEG q=82, EXIF-ориентация
  применена, около 250-400 КБ;
- `faces/<face_id>.jpg` - квадрат 240 px, тот же алгоритм, что в
  `_face_thumbnail`.

Прокси строятся для всех изображений альбома (не только выбранных): это нужно,
чтобы позже показать, из чего выбирали, и проверить модель ранжирования глазами.
Оценка: 1000 кадров - около 350 МБ против 5-10 ГБ оригиналов.

Источник изображения выбирается в одном месте: оригинал, если
`availability = present`, иначе прокси. Через эту функцию идут
`ailbum-media://`, `face.thumbnail` и `layout/assistant.render_variants`.
Окна кропа в `layout_placements` хранятся в долях повёрнутого кадра, поэтому
превью разворотов и редактор раскладки работают на прокси без пересчёта.
Renderer об этом не знает.

### 6. Операция "Заказан" и "Освободить место"

Последовательность для альбома (CLI `ailbum album archive <id>` и кнопка в UI):

1. `draft -> ordered`: фиксируется `ordered_at`; выбор и раскладка становятся
   только для чтения (без явного "вернуть в работу" новые события не пишутся).
2. Экспорт (п. 7) - если для текущей раскладки нет успешного экспорта.
3. Для каждого изображения альбома: построить прокси, проверить, что файл прокси
   читается. Без успешного прокси изображение не архивируется.
4. Перенести оригиналы в Корзину ОС (`shell.trashItem` в Electron,
   `send2trash` в CLI) - обратимо, пока Корзина не очищена. Ailbum не удаляет
   файлы безвозвратно.
5. `availability = archived` для перенесённых, `albums.status = archived`.
6. Удалить записи `feature-cache` для SHA-256, у которых больше нет `present`-копий.

Если оригинал входит в несколько альбомов, он архивируется только когда все
содержащие его альбомы имеют статус `ordered` или `archived`; иначе шаг 4 для него
пропускается и UI сообщает причину.

Пользователь может удалить файлы сам, вне приложения: индексация пометит их
`missing`, UI предложит "подтвердить удаление". В этом случае прокси построить уже
нельзя - архив будет без превью; поэтому рекомендуемый путь - через приложение.

### 7. Экспорт - существующий `export_originals` плюс журнал

Экспорт уже есть: `layout.export` копирует оригиналы размещённых кадров в папку
"Раскладка альбома" с именами `NN-K_<file>` в порядке разворотов и возвращает
список недоступных файлов. Решение не меняет алгоритм, а добавляет:

- таблицу `album_exports(id, album_id, layout_id, selection_hash, folder, count,
  missing_json, exported_at)` - запись о каждом экспорте;
- условие архивации: есть экспорт с `selection_hash`, равным текущему, и пустым
  `missing_json`. Иначе шаг 2 п. 6 повторяет экспорт, а при недоступных файлах
  архивация останавливается.

Каталог экспорта принадлежит пользователю: Ailbum его не архивирует и не удаляет.

Экспорт копирует файлы без кропа: окна кропа применяются на сайте фотокниг
вручную. Рендер кадров по кропу и с проверкой DPI для типографии
(`purpose = print`) - отдельное решение, этот ADR его не вводит.

### 8. Удаление альбома и "забыть"

- Удалить альбом (`draft`): удаляются `albums`, `album_sources`, `album_photos`,
  его `layouts` (каскадом развороты и размещения), `album_exports` и
  `selection_events` альбома - пользователь явно отказывается от этих решений.
  Изображения, анализы, лица и люди остаются.
- Удалить архивный альбом: разрешено только с флагом `--forget-decisions`, иначе
  отказ; архивные решения - основной источник предпочтений.
- `ailbum forget --album <id> | --source <root>`: удаляет изображения, их анализы,
  лица, сканы объектов, размещения, события и прокси, затем пересчитывает центроиды
  затронутых людей; человек без единого лица удаляется. Единственная операция,
  которая делает `DELETE FROM images`; требует подтверждения со списком того, что
  пропадёт.

### 9. Идентичность изображения по содержимому

`_upsert_image` при отсутствии строки с таким `path` ищет строку с тем же
`sha256` и `availability IN ('missing', 'archived')`; если находит ровно одну -
обновляет её `path`, `source_root`, `relative_path` и ставит `present`. История,
лица, раскладки и решения привязываются к вернувшемуся файлу. Если совпадений
несколько, создаётся новая строка (точные дубликаты в разных местах остаются
раздельными).

## Рассмотренные альтернативы

| Вариант | Почему отклонён |
| --- | --- |
| Отдельная база на каждый альбом + общая база людей | Две базы с перекрёстными ID лиц, сложная синхронизация `person_id`; предпочтения разбросаны по файлам |
| Хранить только `people` (центроиды), лица удалять вместе с оригиналами | Центроид замораживается, ручные исправления нельзя пересчитать, нет данных для смены модели эмбеддингов |
| Не делать прокси, хранить только метаданные | Архивный альбом, раскладка и база лиц становятся невизуальными; нельзя проверить подборки и ошибки распознавания |
| Хранить пережатые копии оригиналов (2-3 МП) | В 5-10 раз больше места, чем прокси 1600 px; для печати всё равно непригодны |
| Оставить раскладку привязанной к `run_id` | Повторный анализ теряет раскладку заказанного альбома, а `layouts.run_id UNIQUE` не даёт хранить её для альбома |
| Безвозвратное удаление файлов приложением | Необратимо при ошибке в выборке альбома; Корзина даёт страховку бесплатно |

## Последствия

Плюсы:

- база людей и предпочтений (выбор, пожелания к раскладке) растёт с каждым
  альбомом и переживает удаление оригиналов;
- повторный анализ не сбрасывает ручной выбор и раскладку;
- вернувшиеся из бэкапа файлы автоматически получают свою историю;
- место на диске освобождается одной операцией с проверкой экспорта и прокси до
  удаления.

Минусы и риски:

- база и `.ailbum/proxies/` растут без ограничения (оценка: ~35 МБ SQLite и
  ~350 МБ прокси на 1000 кадров) - нужна команда статистики занимаемого места;
- `.ailbum/` становится единственной копией знаний - требуется бэкап
  (`VACUUM INTO` + копия `proxies/`), иначе потеря диска = потеря базы лиц;
- центроид по всем лицам за годы смещается для детей и меняющейся внешности;
  взвешивание по давности - отдельное решение;
- новый CV-анализ архивных фото невозможен: смена модели лиц, CLIP или YOLOX не
  пересчитает эмбеддинги и сканы для архива. Старые люди останутся привязаны к
  старой `embedding_model`, сопоставление с новой моделью потребует оригиналов или
  повторного распознавания по прокси (качество хуже);
- повторный экспорт архивного альбома невозможен - его результат живёт только в
  папке пользователя;
- `ON DELETE RESTRICT` ломает текущие сценарии, полагающиеся на каскад, - их нужно
  перевести на `forget`;
- ADR 0002 нужно перенумеровать на свободную версию схемы и согласовать
  `selection_events.album_id`.

## План внедрения

1. Миграция схемы на следующую свободную версию после ADR 0002 (сейчас 11 -> 12,
   если этот ADR внедряется первым): `albums`, `album_sources`, `album_photos`,
   `album_exports`, `images.availability`, `layouts.album_id` и `layouts.prompt`,
   `RESTRICT` на внешних ключах (пересоздание таблиц, т. к. SQLite не меняет FK
   через `ALTER`). Для каждого `run_id` с записями в `photo_selections`,
   `desktop_run_settings` или `layouts` создаётся альбом `draft`; выбор переносится
   в `album_photos`, раскладка получает `album_id`; старые таблицы выбора удаляются.
2. Перевод desktop API выбора и `layout.*` с `run_id` на `album_id`; согласование
   `selection_events` с ADR 0002.
3. Сопоставление по SHA-256 в `_upsert_image`.
4. Прокси и единая функция источника изображения для `ailbum-media://`,
   `face.thumbnail` и `render_variants`.
5. Запись `album_exports` в `export_originals`.
6. Архивация альбома с переносом в Корзину и чисткой `feature-cache`.
7. `forget` и `ailbum db usage` (размер базы, прокси, кэша).
